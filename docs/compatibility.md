# Compatibility and operating limits

The [AWS operations chart and measured test results](../COMPATIBILITY.md) track protocol support and conformance findings. This document describes storage and operating limits, not an S3 certification.

| Area | Current behavior |
| --- | --- |
| Authentication | SigV4 headers/presigned URLs; static operator plus opt-in JWT AssumeRoleWithWebIdentity sessions; bucket-tag ABAC; no anonymous, full IAM, SigV2 or SigV4a |
| Addressing | Path-style; optional virtual-host style |
| Buckets | Create, head, list, delete empty bucket, location, enabled/suspended versioning |
| Objects | Put, get, head, delete, batch delete, streaming copy, GetObjectAttributes |
| Reads | Single, suffix, and open-ended byte ranges; completed-part GET/HEAD; ETag/date conditions; response header overrides; checksums scoped to response bytes |
| Writes | `If-Match` / `If-None-Match`; complete bytes published atomically |
| Listing | V1/V2, prefix, delimiter, pagination, URL encoding |
| Versioning | Unique versions, null versions, delete markers, version reads/copies/deletes, version listing, native latest-path restoration |
| ACLs | Private bucket/object ACLs and version-specific owner grants; one configured principal |
| Multipart | Initiate, upload, copy part, list parts/uploads, complete, abort; persistent state and completion retry |
| Integrity | Content-MD5, SHA256 payload validation, CRC32, CRC32C, CRC64NVME, SHA1, SHA256; signed chunks and checksum trailers; uploads without a client checksum receive a CRC64NVME full-object checksum as on S3 |
| Metadata | Content headers, website redirect location, user metadata, object/version tags, completed-part descriptors; `.gateway/metadata/<id>` helpers on all providers, referenced by cloud native metadata or disk file identity |
| Notifications | SNS topic configurations, prefix/suffix filters, object create/remove events, durable publication retry queue |
| ABAC | Bucket status and S3 Control tagging APIs; JWT roles with a validated IAM policy subset |
| Lifecycle | Configuration and background execution: current/noncurrent expiration, retention count, delete-marker cleanup, abandoned multipart cleanup; prefix/tag/size filters |
| Unsupported | Public/cross-user ACLs, IAM/bucket policies, MFA Delete, SSE request semantics, object lock, storage-class transitions, SQS/Lambda/EventBridge notifications, browser POST, select, restore |

Unsupported recognized features return an S3 error rather than silently claiming support. Private ACLs and explicit owner-only grants are persisted, while the configured principal retains owner access. Public/group/other-user grants are rejected. These S3 ACLs do not modify Azure IAM or public container policies. `STANDARD` is the only accepted S3 storage class. Native Azure encryption remains an Azure account concern; accepting S3 encryption headers would require additional implementation.

Some finer compatibility details remain incomplete: part-number reads for legacy multipart objects without saved boundaries and newline-prefix listing behavior in Ceph. Unicode metadata uses [AWS-documented RFC 2047 response encoding](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html), which differs from Ceph's raw-header assertion. Multipart delimiter listing and checksum fields in copy-part/list-parts/completion XML have Docker client coverage. Core tests exercise common paths; arbitrary combinations of S3 features are not yet certified.

## Transparency boundaries

**Disk.** Buckets are directories and keys are relative file paths. The root `.gateway` directory and each bucket's `.gateway/` object prefix are reserved. The same object prefix is reserved on cloud backends. Existing regular files are readable and derive ETags from their contents. Filesystem case folding, component/path length limits, and file/directory collisions constrain the key space. Do not mount a case-insensitive disk when case-distinct object names are required.

Disk helpers live inside each bucket at `.gateway/metadata/<id>`, indexed by the object key and its inode, modification time and size. Files contain only object bytes; no extended attributes or embedded references are required. Staging and the process lock remain in the root `.gateway` directory, on the same filesystem as the bucket files. Metadata is durable before atomic file publication; maintenance removes obsolete generations. Reads of existing native files do not create helpers. Atomic native replacement invalidates saved metadata even when size and modification time match. Native in-place edits that preserve both fields are not reliably detectable; copying a data directory to new inodes also breaks saved metadata associations. Reads whose metadata has already been resolved use the open file's generation directly, avoiding another helper read or content hash.

Metadata records are selected by file size and nanosecond modification time. A native overwrite that changes either invalidates saved S3 metadata. A native writer that preserves both can leave stale metadata; modify objects through the gateway when preserving S3 metadata and conditional semantics matters. Symlinks are rejected, and the tree must not be modified by an untrusted local process. Use atomic replacement for native writers; in-place mutation can affect an ongoing read.

Disk uses a process lock and atomic file rename. Only one gateway process can open a root. Files and their metadata are synced before publication, but this is not a fully audited crash-consistent filesystem database. Maintenance removes unreferenced metadata generations after a 24-hour grace period. Startup removes abandoned backend staging files after acquiring the exclusive root lock. Directory timestamps currently supply disk bucket creation dates, including for native buckets.

**Azure.** Container/blob names are preserved, so Azure naming and metadata limits apply. For example, S3 bucket names containing dots cannot become native Azure containers. Existing blobs do not require migration. Blobs without gateway metadata use native Content-MD5 where present, otherwise an opaque Azure ETag. ETags must be treated as opaque by clients.

Uploaded blobs bind gateway metadata to native Content-MD5 and size. Native server-side assemblies have no computable full-object MD5, so their envelopes bind to size and preserve the frontend ETag/checksums directly. Native writers must discard reserved gateway metadata when replacing content. Native user metadata edits remain visible through S3.

Private ACL and object tag updates use conditional Azure SetMetadata, preserving bytes, frontend ETag and modification time without reading the object.

The full gateway metadata record lives in an immutable SHA256-addressed helper under `.gateway/metadata/`. The native `gateway` field contains only a format version and a reference; the helper is written before atomically publishing that reference. Reads verify the helper digest and fail if the helper is missing or corrupt. Native bytes and compatible user metadata remain accessible. Helpers may be shared by versions; maintenance collects only unreferenced helpers after a 24-hour grace period. Tags live in the gateway helper and are not mirrored into Azure Blob Index Tags.

Azure puts stage blocks and commit bytes, properties, and metadata together. Conditions use Azure ETags for compare-and-swap. Bucket deletion is protected from concurrent mutations within the same gateway process. Azure does not provide atomic "delete only if empty" container deletion; concurrent writers outside that process can race it. Use a single gateway instance and avoid native writers during bucket deletion. Azure snapshots, leases, soft deletion, and account retention settings can affect deletion and are not mapped to S3 versioning.

**AWS/RustFS.** The `backend/aws` adapter uses AWS Go SDK v2 with a separate upstream endpoint, region and credential chain. Native current keys, content headers, metadata, immutable version references and conditional writes are used. Large upstream writes use native multipart transfers. Native ETags are concurrency tokens; frontend ETags preserve gateway semantics. The gateway retains bucket settings, logical history indexes, journals and multipart receipts in `.gateway/`. A bucket with unrelated native historical versions is not automatically emptied by DeleteBucket. Required upstream permissions include listing/read/write/delete, bucket/versioning operations, version reads/deletes, and native multipart operations. Provider encryption/retention policies still apply.

Website redirect locations are returned as object metadata; the gateway does not host S3 websites. AWS writes use the native redirect property. The existing metadata envelope preserves it on providers such as RustFS that omit that property. CopyObject carries the redirect only when the request explicitly supplies it, including with the COPY metadata directive.

The `.gateway/` namespace and `gateway` native metadata reference are reserved. No migration from earlier helper layouts is provided. Native modifications that copy stale gateway metadata can invalidate its contents; route writes through the gateway when logical versioning or authorization matters.

## Identity and notifications

See [configuration and examples](../README.md#jwt-roles-and-bucket-abac) for the JWT trust configuration, supported policy subset and SNS setup. Session policies default to deny and explicit Deny takes precedence. Bucket resource tags are available to conditions only while ABAC is enabled. Administrative mutations require the static operator credentials; sessions can perform granted data actions and configuration reads. ABAC does not configure provider IAM or Azure RBAC. Existing sessions and presigned URLs are reevaluated against bucket tags on every request. Authorization and provider mutation are not a distributed transaction; an already authorized request may finish while an administrator changes tags.

SNS delivery is at least once for persisted queue entries, with no FIFO or exactly-once guarantee. Create/remove events are queued before acknowledging successful gateway mutations; failed SNS publishes survive restart. There is a crash window between object publication and queue insertion for unacknowledged requests. Delivered receipts are collected after 24 hours, and repeated multipart completion after that period may emit another event. Queue storage has no admission limit yet; monitor it during a prolonged SNS outage. Pending events prevent bucket deletion. Direct provider writes and lifecycle expiration do not emit these request notifications. Notifications to unsupported destinations/events are rejected.

## Bucket settings and lifecycle

Bucket tags allow 50 entries; object tags retain their ten-entry limit. CORS stores up to 100 rules and validates preflight origin, method and headers. An allowed origin does not bypass S3 authentication. Ownership controls persist all three modes; with the single configured principal, BucketOwnerPreferred and ObjectWriter have no cross-user distinction. BucketOwnerEnforced rejects ACL updates and uploads with incompatible ACLs. New gateway buckets default to BucketOwnerEnforced. Uploads with no ACL, `private`, or `bucket-owner-full-control` are accepted; explicit ACL updates require changing or removing the ownership controls. Existing native buckets without saved ownership controls retain the private ACL model.

New gateway buckets enable all four PublicAccessBlock flags; subsequent changes are persisted. BlockPublicAcls denies public canned ACL requests. Removing or clearing flags never enables anonymous/public access: public/group/cross-user grants and bucket policies remain unsupported. These settings do not change Azure public container access or IAM.

Both cloud providers store bucket settings as one JSON object at `.gateway/settings`; missing settings mean the default configuration. Reads do not backfill existing native objects or create settings. There is no migration reader for the previous Azure container-metadata settings layout. Unreferenced object metadata manifests and superseded gateway-owned native versions are collected after a 24-hour grace period. Collection traces all native blob metadata, including immutable versions and multipart parts, under the backend maintenance lock; corrupt references stop collection.

The executable runs lifecycle scans once per minute by default (`GATEWAY_LIFECYCLE_INTERVAL` / `-lifecycle-interval`). It applies only explicitly enabled bucket rules; read-only mode disables execution. Applications embedding `gateway.New` must schedule `RunLifecycleOnce`, `RunMaintenanceOnce` and `RunNotificationsOnce` themselves. Current/noncurrent expiration, retained noncurrent counts, expired delete markers and incomplete multipart cleanup are implemented. Prefix, tag, size and And filters are supported. Storage-class transitions are rejected, not merely stored. Up to 1,000 rules and positive retention periods up to 365,000 days are accepted.

Day-based deadlines round up to midnight UTC; date-based rules require midnight UTC. Expiration is asynchronous, with work due on a subsequent scan. Multipart completion/abort and lifecycle abort share upload locks. Object/version expiration rechecks current metadata under the same object lock as writes and tagging, while preventing concurrent bucket configuration changes. Noncurrent age is persisted so deleting an intermediate version cannot reset it. Native writes still bypass managed versioning and can invalidate metadata; use one gateway writer when lifecycle and version history matter.

`GATEWAY_TEST_LIFECYCLE_DAY` / `-test-lifecycle-day` is an explicit test-only override (production default `0s`). The disposable Docker fixtures use `1s` with 250 ms scans and Ceph's `lc_debug_interval=1`. HTTP expiration headers retain normal UTC-day dates even in those fixtures. Unit/SDK tests advance scan time directly to verify production deadlines without sleeps. Lifecycle scans currently enumerate buckets and version indexes; large namespaces need the same pagination/indexing improvements as ordinary version listing.

Age-based expiration is not aware of Iceberg references or snapshots. Configure it only for data with a known retention policy; Iceberg table cleanup should be driven by the catalog/table maintenance process.

## Scale and recovery

Cloud GETs read bytes, native properties and the gateway reference from the same native response, without a preceding HEAD. For an unversioned bucket with no pending recovery, native objects without a gateway reference require three provider requests for ordinary gateway GET or HEAD on both S3 and Azure: bucket settings, the key's pending-publication check, and the object operation. Gateway-written objects require one additional request for their metadata helper (four total). Conditional/range GETs resolve metadata first and guard the download with the native revision, reusing the resolved metadata: a successful range GET requires four requests for native objects or five for gateway-written objects. Bucket settings are shared only within the current read request, so later requests observe configuration and authorization changes. Historical versions, recovery and SDK retries can require additional calls. S3 listings still fetch object metadata individually to preserve frontend ETags and other saved fields.

Versioning uses provider-native immutable versions on AWS/RustFS and on Azure accounts with blob versioning enabled. The gateway retains its own version IDs, logical indexes and recovery journals. Disk and Azure accounts without native versioning retain immutable helper copies plus the latest native object. Azure account settings are never changed; enabling S3 gateway versioning enables underlying AWS/RustFS versioning, which stays enabled during logical suspension. Existing native objects are preserved as null versions on their first S3 mutation after enabling versioning. Run one gateway process for the complete bucket namespace visible to its storage credentials, including background maintenance. Even instances intended for disjoint buckets would scan each other’s state unless their provider permissions isolate those buckets. All writes/deletes to versioned buckets must go through that process: native writers and multiple Azure gateway instances cannot participate in version history or recovery. Native reads continue to work; a delete marker removes the native current path, and deleting the latest version republishes its predecessor.

Version indexes and publication journals live in each bucket's `.gateway/versions/` namespace on all three backends. Bucket settings live at `.gateway/settings`. The shared layer serializes operations on the same key; unrelated object reads and writes can proceed concurrently. Bucket configuration changes, deletion and recovery/maintenance scans remain exclusive. Interrupted publication is replayed before subsequent S3 reads/listing/mutations. Fault-injection tests exercise write/delete and lifecycle publication recovery. Publication across the history record and native path is not an atomic transaction for native readers, and a failed or disconnected request may finish during journal replay. Corrupt/missing helper state fails rather than inventing history.

Both cloud backends reserve `gateway` object metadata for a small reference to `.gateway/metadata/<id>`. The helper holds the full gateway record, including frontend ETags, checksums, ACLs, tags, logical version IDs and completed-part boundaries. S3 streaming uploads use a write-once helper because final checksums are unavailable at multipart initiation. Gateway multipart state lives in `.gateway/<upload-id>/manifest` and `parts/`, with temporary `.gateway/incoming/` objects. Configured notifications use `.gateway/notifications/` for durable retry records. Native-version references are encoded internal identifiers, not additional objects. Helper objects are hidden from gateway clients but visible to clients accessing the provider directly.

Version listing scans indexes and native objects; each key's index contains its entire version history. Listing pagination after the marker version has been permanently removed skips the rest of that key. Maintenance removes unreferenced immutable data, obsolete disk metadata generations, and Azure helper blobs after a 24-hour grace period. It checks references under publication locks and preserves all retained versions and active uploads. Completed multipart receipts are retained indefinitely; incomplete uploads require an explicit abort or lifecycle rule. This is not yet a design for very large histories or distributed writers.

Single puts and individual multipart parts are limited to 5 GiB; non-final multipart parts must be at least 5 MiB. Cloud uploads use four parallel 8 MiB buffers with backpressure instead of full-object staging files. Native multipart/block commit occurs only after end-of-stream integrity validation. S3 streaming multipart metadata uses a write-once receipt under `.gateway/metadata/` because the final digest is unavailable at initiation. Azure multipart assembly uses server-side block copies up to 4000 MiB per block; S3 uses server-side part copies up to 5 GiB. Completion derives composite checksums and full-object CRCs from saved part metadata without reading payload bytes. Failed publication retains parts for retry; uploaded parts are temporarily isolated under `.gateway/incoming/` and abandoned incoming objects are collected after the maintenance grace period. Azurite's explicit APINotImplemented response uses a streaming copy fallback. Disk uploads and checksummed copy operations can still spool to disk. No throughput SLA or global upload concurrency limit is provided.

Disk listing walks and sorts the tree. Azure listing starts at the prefix and skips through the continuation key. Both need indexing/cursor work for large namespaces. Native disk objects without saved metadata require content hashing when listed. There is no upload concurrency admission limit or automatic temporary-disk quota management yet.

Multipart coordination uses locks in one gateway process. Incoming part bodies are staged outside the upload lock; part commits can run concurrently, while completion and abort exclude commits and recheck upload state. Multiple Azure gateway instances must not operate on the same multipart upload. Completed manifests are retained to serve retry requests and currently have no expiry. Cloud completion durably journals source references and the selected version plus its completion manifest before assembling the native destination. Disk completion stages immutable bytes first. Providers without native history retain an immutable copy when logical versioning is enabled. The journal is removed only after native publication, the version index (when applicable), and the completion receipt are durable. This covers unversioned, enabled and suspended buckets. An accepted intent finishes without reevaluating its original write condition. Matching retries return the original ETag, checksums and version ID, including after later writes/deletes; changed parts or completion conditions/checksum headers are rejected. Failed preconditions leave the upload available. Cleanup failures are retried in maintenance and do not turn committed completion into an error. Fault tests inject failures before and after each publication boundary; distributed writers remain unsupported.

Recovery and helper collection run at startup and at the lifecycle scan interval, even without lifecycle rules. Read-only mode disables the worker. The cleanup grace period always uses real time, independently of the test lifecycle clock. Maintenance enumerates metadata and can pause writes while tracing references, so very large namespaces need further indexing and scheduling work.

On Unix, request/copy/completion staging files are unlinked immediately and reclaimed when their last descriptor closes, including process exit. Disk backend staging left by a crash is removed at startup only after acquiring the exclusive root lock. Other platforms retain normal deferred temporary-file cleanup.

1. Continue triaging remaining Ceph discrepancies against AWS semantics; some RGW tests deliberately differ, including missing-object conditional deletes.
2. Extend the Iceberg Parquet append/scan coverage with concurrent catalog commit scenarios.
3. Expand account-specific Azure/S3 behavior and large-object coverage beyond the live native-history, recovery and metadata tests.
4. Improve pagination and maintenance-scan scale, receipt retention controls, and request resource limits.
5. Add identities and other S3 APIs only with explicit storage semantics and conformance tests; expand versioning boundary and concurrency coverage.
